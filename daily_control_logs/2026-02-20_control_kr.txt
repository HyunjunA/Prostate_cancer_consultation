■ 상세 수정 가이드

  이 수정이 효과적인 이유:
  경로 탐색 공격은 "../"를 사용하여 의도된 디렉토리 밖의 파일에 접근합니다.
  다층 방어(defense-in-depth)로 두 가지 검증을 함께 사용합니다:

  1) regex 허용 목록 (^[a-zA-Z0-9][a-zA-Z0-9_-]{0,254}$):
     입력에서 . / \ 등 경로 구분자를 원천 차단합니다. 허용된 문자(영숫자,
     하이픈, 언더스코어)만 통과시키므로 "../" 자체가 불가능합니다.

  2) resolve() 경로 확인:
     regex를 우회하는 미지의 인코딩 공격에 대비한 2차 방어입니다.
     실제 파일 경로를 resolve()로 절대 경로로 변환한 후, 그 경로가
     _UPLOAD_DIR 내부인지 확인합니다. 이중 인코딩이나 유니코드 트릭으로
     regex를 우회하더라도 이 검증이 최종 방어선이 됩니다.

  둘 다 필요한 이유: regex만 사용하면 미지의 인코딩 우회가 가능할 수 있고,
  resolve()만 사용하면 심볼릭 링크 공격 등에 취약할 수 있습니다.

  단계별 구현:
  1. routes_transcript.py 상단에 import re 추가 (이미 있을 수 있음)
  2. _PATIENT_ID_PATTERN 상수와 _validate_patient_id() 함수 추가 (약 73행 근처)
  3. _xlsx_path() 함수 호출 전에 _validate_patient_id() 호출 추가
  4. _save_xlsx() 함수에서도 _validate_patient_id() 호출 추가
  5. 영향받는 4개 엔드포인트 모두에 검증 적용:
     - GET  /download/{patient_id}        (162행)
     - GET  /download-batch?patient_ids=   (319행) — 각 patient_id에 대해
     - POST /analyze                       (_save_xlsx 내부)
     - POST /analyze-batch                 (_save_xlsx 내부)

  코드 — 수정 후 (안전):
    import re
    from pathlib import Path

    _UPLOAD_DIR = Path("/app/uploads")
    _PATIENT_ID_PATTERN = re.compile(r'^[a-zA-Z0-9][a-zA-Z0-9_-]{0,254}$')

    def _validate_patient_id(patient_id: str) -> str:
        """다층 방어: regex 허용 목록 + resolve() 경로 확인."""
        # 1차 방어: 허용된 문자만 통과 (. / \ 등 차단)
        if not _PATIENT_ID_PATTERN.match(patient_id):
            raise HTTPException(400, "Invalid patient_id format")

        # 2차 방어: 해석된 경로가 uploads 디렉토리 내부인지 확인
        resolved = (_UPLOAD_DIR / f"{patient_id}_predictions.xlsx").resolve()
        if not str(resolved).startswith(str(_UPLOAD_DIR.resolve())):
            raise HTTPException(400, "Invalid patient_id")

        return patient_id

    def _xlsx_path(patient_id: str) -> Path:
        _validate_patient_id(patient_id)  # 경로 생성 전 검증
        return _UPLOAD_DIR / f"{patient_id}_predictions.xlsx"

    def _save_xlsx(patient_id: str, xlsx_bytes: bytes) -> None:
        _validate_patient_id(patient_id)  # 파일 쓰기 전 검증
        _UPLOAD_DIR.mkdir(parents=True, exist_ok=True)
        _xlsx_path(patient_id).write_bytes(xlsx_bytes)

■ 쉬운 설명 (비유)

  자물쇠 비밀번호를 맞추는 상황을 상상해보세요. 대부분의 자물쇠는 맞든 틀리든
  같은 반응을 보여줍니다. 그런데 결함이 있는 자물쇠가 첫 번째 숫자를 맞추면
  살짝 더 오래 걸린다면? 10개 숫자를 모두 시도하고, 가장 오래 걸리는 것
  (정답!)을 찾고, 다음 자리로 넘어갈 수 있습니다. 4자리 자물쇠의 경우
  10,000번이 아니라 40번(자리당 10개 × 4자리)만 시도하면 됩니다.

  Python의 == 연산자는 문자열을 한 글자씩 비교하고 첫 불일치에서 멈춥니다.
  공격자가 "s"로 시작하는 키를 보내면 (첫 글자 정답), "x"로 시작할 때보다
  비교가 한 글자 더 진행되어 살짝 더 오래 걸립니다.

  또한 시스템의 모든 사용자가 동일한 하나의 API 키를 공유합니다:
  - 서버는 누가 요청하는지 구분 불가
  - 한 사람의 키가 유출되면 전체가 위험
  - 특정 사용자의 접근만 차단할 방법 없음

■ 상세 수정 가이드

  이 수정이 효과적인 이유:
  Python의 == 연산자는 문자열을 한 글자씩 비교하고 첫 불일치에서 즉시 멈춥니다.
  이로 인해 첫 글자가 맞는 키는 틀린 키보다 비교에 미세하게 더 오래 걸립니다.
  hmac.compare_digest()는 "상수 시간 비교(constant-time comparison)"를 수행합니다.
  즉, 첫 글자가 맞든 틀리든 항상 전체 문자열을 끝까지 비교하여 동일한 시간이
  걸립니다. 이로써 응답 시간 차이로 키를 추측하는 것이 불가능해집니다.
  또한 사용자별 JWT 토큰으로 전환하면 사용자 식별, 개별 키 폐기, 접근 제어가
  가능해집니다.

  단계별 구현:
  [즉시 — 타이밍 공격 방지, 15분]:
  1. routes_transcript.py:73-82 에서 _verify_api_key 함수 수정
  2. routes_nlp.py:37-46 에서 동일하게 수정
  3. if api_key != _API_KEY 를 hmac.compare_digest()로 교체

  [중기 — JWT 마이그레이션, 2-4시간]:

  코드 — 수정 후 (안전):
    # [즉시] 상수 시간 비교
    import hmac

    _API_KEY = os.environ["API_KEY"]  # 기본값 제거 (취약점 8)

    async def _verify_api_key(x_api_key: str = Header(..., alias="X-API-Key")):
        if not hmac.compare_digest(x_api_key, _API_KEY):  # 상수 시간 비교
            raise HTTPException(403, "Invalid API Key")
        return x_api_key

    # [중기] JWT 인증으로 전환
    from jose import JWTError, jwt
    from datetime import datetime, timedelta

    SECRET_KEY = os.environ["JWT_SECRET_KEY"]
    ALGORITHM = "HS256"
    ACCESS_TOKEN_EXPIRE_MINUTES = 60

    def create_access_token(data: dict) -> str:
        to_encode = data.copy()
        expire = datetime.utcnow() + timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES)
        to_encode.update({"exp": expire})
        return jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)

    async def get_current_user(token: str = Header(..., alias="Authorization")):
        try:
            token = token.replace("Bearer ", "")
            payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
            user_id: str = payload.get("sub")
            if user_id is None:
                raise HTTPException(401, "Invalid token")
            return user_id
        except JWTError:
            raise HTTPException(401, "Invalid token")

  우선순위 & 소요 시간: 높음 — hmac 수정은 즉시 적용 가능 | 15분 (타이밍) + 2-4시간 (JWT)
  의존성: 타이밍 수정은 독립적. JWT는 취약점 3(접근 제어)과 취약점 5(감사 로그)의 전제 조건

■ 상세 수정 가이드

  이 수정이 효과적인 이유:
  현재 시스템은 "인증(authentication)"만 있고 "인가(authorization)"가 없습니다.
  인증은 "당신이 누구인지" 확인하고, 인가는 "당신이 무엇을 할 수 있는지"
  확인합니다. API 키를 가진 모든 사용자가 모든 환자 데이터에 접근 가능한 것은
  인가가 없기 때문입니다. user_patient_access 테이블로 "이 사용자가 이 환자를
  볼 수 있는가?"를 확인하면, 각 의사가 자신의 환자만 접근하도록 제한됩니다.
  단계적으로 구현하여 기존 시스템을 점진적으로 강화합니다.

  단계별 구현:

  [1단계 — 즉시] patient_id 형식 검증:
  1. 취약점 1의 _validate_patient_id() 함수를 모든 환자 관련 엔드포인트에 적용
  2. 이것만으로 경로 탐색은 차단되지만, 인가는 아직 미구현

  [2단계 — 중기] 사용자별 인증 + 접근 제어:

  3. 각 엔드포인트에서 JWT로 사용자 식별 후 접근 권한 확인
  4. 미인가 접근 시 403 반환

    CREATE TABLE users (
        id SERIAL PRIMARY KEY,
        username VARCHAR(100) UNIQUE NOT NULL,
        password_hash VARCHAR(255) NOT NULL,
        role VARCHAR(50) DEFAULT 'researcher',  -- admin, physician, researcher, readonly
        is_active BOOLEAN DEFAULT TRUE,
        created_at TIMESTAMP DEFAULT NOW()
    );

    CREATE TABLE user_patient_access (
        id SERIAL PRIMARY KEY,
        user_id INTEGER REFERENCES users(id),
        patient_id VARCHAR(255) NOT NULL,
        access_level VARCHAR(20) DEFAULT 'read',  -- read, write, admin
        granted_by INTEGER REFERENCES users(id),
        granted_at TIMESTAMP DEFAULT NOW(),
        UNIQUE(user_id, patient_id)
    );

        patient_id: str,
        current_user: User = Depends(get_current_user),
        db: Session = Depends(get_db)
    ) -> User:
        # admin은 모든 접근 허용
        if current_user.role == "admin":
            return current_user

        access = db.query(UserPatientAccess).filter(
            UserPatientAccess.user_id == current_user.id,
            UserPatientAccess.patient_id == patient_id
        ).first()

        if not access:
            raise HTTPException(403, "Access denied for this patient")
        return current_user

    @router.get("/download/{patient_id}")

        patient_id: str,
        current_user: User = Depends(verify_patient_access),
        db: Session = Depends(get_db)

        # current_user가 이 patient_id에 접근 권한이 있음이 확인됨

        return FileResponse(path)

  접근을 기록하도록 요구합니다: 누가, 무엇을, 언제, 어디서. 이것 없이는
  데이터 침해를 감지조차 할 수 없고, 조사는 불가능합니다.

  누가 어떤 환자 데이터에 언제 접근했는지 기록 없음.
  HIPAA는 모든 PHI 접근에 대한 감사 추적을 요구.

  수정: audit_log 테이블에 user_id, action, patient_id, endpoint,
  status, timestamp, ip_address를 모든 환자 데이터 엔드포인트에 대해 기록.

■ 상세 수정 가이드

  이 수정이 효과적인 이유:
  감사 로그는 "누가, 무엇을, 언제, 어디서" 환자 데이터에 접근했는지를 기록합니다.
  HIPAA는 모든 PHI 접근에 대한 감사 추적(audit trail)을 요구합니다. 감사 로그
  없이는 데이터 침해를 감지할 수 없고, 사고 발생 시 조사가 불가능합니다.
  DB 테이블에 로그를 저장하면 쿼리로 검색/분석이 가능하고, 미들웨어로 구현하면
  모든 엔드포인트에 일관되게 적용됩니다. 비동기 저장으로 성능 영향을 최소화합니다.

  단계별 구현:
  1. PostgreSQL에 audit_log 테이블 생성 (아래 DDL 참조)
  2. models.py에 AuditLog SQLAlchemy 모델 추가
  3. 감사 로깅 미들웨어 또는 유틸리티 함수 작성
  4. 모든 PHI 관련 엔드포인트에서 감사 로그 기록
     (download, download-batch, predictions, history, surveys 관련 전부)
  5. 감사 로그 조회 관리자 엔드포인트 추가 (선택)

  코드 — 수정 후 (안전):
    # 1. DDL — audit_log 테이블 생성
    CREATE TABLE audit_log (
        id SERIAL PRIMARY KEY,
        user_id VARCHAR(255),         -- API 키 또는 JWT에서 추출한 사용자 ID
        action VARCHAR(50) NOT NULL,  -- download, view, analyze, delete 등
        patient_id VARCHAR(255),      -- 접근한 환자 ID
        endpoint VARCHAR(255) NOT NULL, -- /api/transcript/download/sid-01
        method VARCHAR(10) NOT NULL,  -- GET, POST, DELETE
        status_code INTEGER,          -- HTTP 응답 코드
        ip_address VARCHAR(45),       -- 클라이언트 IP (IPv6 지원)
        user_agent TEXT,              -- 브라우저/클라이언트 정보
        request_metadata JSONB,       -- 추가 메타데이터 (쿼리 파라미터 등)
        created_at TIMESTAMP DEFAULT NOW()
    );
    CREATE INDEX idx_audit_patient ON audit_log(patient_id);
    CREATE INDEX idx_audit_user ON audit_log(user_id);
    CREATE INDEX idx_audit_created ON audit_log(created_at);

    # 2. models.py — SQLAlchemy 모델
    class AuditLog(Base):
        __tablename__ = "audit_log"
        id = Column(Integer, primary_key=True, autoincrement=True)
        user_id = Column(String(255))
        action = Column(String(50), nullable=False)
        patient_id = Column(String(255))
        endpoint = Column(String(255), nullable=False)
        method = Column(String(10), nullable=False)
        status_code = Column(Integer)
        ip_address = Column(String(45))
        user_agent = Column(Text)
        request_metadata = Column(JSON)
        created_at = Column(DateTime, server_default=func.now())

    # 3. 감사 로깅 유틸리티
    async def log_audit(db: Session, request: Request, action: str,
                        patient_id: str = None, status_code: int = 200):
        try:
            entry = AuditLog(
                user_id=request.state.user_id if hasattr(request.state, 'user_id') else "unknown",
                action=action,
                patient_id=patient_id,
                endpoint=str(request.url.path),
                method=request.method,
                status_code=status_code,
                ip_address=request.client.host,
                user_agent=request.headers.get("user-agent")
            )
            db.add(entry)
            db.commit()
        except Exception:
            db.rollback()  # 감사 로그 실패가 요청을 중단시키지 않도록

    # 4. 엔드포인트에서 사용
    @router.get("/download/{patient_id}")
    async def download(patient_id: str, request: Request,
                       api_key: str = Depends(_verify_api_key),
                       db: Session = Depends(get_db)):
        await log_audit(db, request, "download", patient_id)
        path = _xlsx_path(patient_id)
        return FileResponse(path)

    from fastapi import APIRouter, Depends, Header, HTTPException
    import hmac

    _API_KEY = os.environ["API_KEY"]

    async def _verify_api_key(x_api_key: str = Header(..., alias="X-API-Key")):

        return x_api_key

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 쉬운 설명 (비유)

  은행의 휴게실 화이트보드에 계좌번호와 부분 비밀번호를 적어놓은 것을
  상상해보세요. 화이트보드는 "내부용"이지만, 은행에서 일하는 모든 사람
  (또는 휴게실에 접근하는 사람)이 볼 수 있습니다.

  우리 서버는 디버깅용 print() 문으로 로그에 다음을 기록합니다:
  - REDCap API 토큰 (부분): "Token: BB714F7B...D26A"
  - 전체 환자 설문 응답 (치료에 대한 환자의 답변)
  - 파일명과 speaker 식별자

  Docker 접근 권한이 있는 사람(개발자, IT 직원, 또는 서버에 접근한
  공격자)이 "docker logs"를 실행하면 이 모든 정보를 볼 수 있습니다.

■ 취약 코드

  routes_surveys.py:1188 (활성 코드):
    print(f"[CONFIG] Token: {REDCAP_API_TOKEN[:8]}...{REDCAP_API_TOKEN[-4:]}")

  routes_surveys.py:798-808 (활성 코드):
    print(f"[SPEAKER] {submission.speaker}")
    print(json.dumps(submission.answers, indent=2, ensure_ascii=False))

■ 문제

  Docker 컨테이너 로그에 다음이 포함됨:
  - 부분 REDCap API 토큰
  - 전체 환자 설문 응답 (PHI)
  - 파일 식별자 및 speaker ID

■ 공격 시나리오 L — 로그 수집

    docker logs prostatecancer-backend 2>&1 | grep -i "token"
    → 부분 REDCap 토큰 노출

    docker logs prostatecancer-backend 2>&1 | grep -A 20 "ANSWERS"
    → 전체 설문 응답(PHI) 평문 확인 가능

■ 수정 방법

  print()를 logging 모듈로 교체.
  프로덕션에서 로그 레벨을 WARNING으로 설정.
  토큰, 키, 환자 데이터 로깅 금지.

■ 상세 수정 가이드

  이 수정이 효과적인 이유:
  print()는 항상 stdout에 출력되며 로그 레벨 제어, 포맷팅, 필터링이 불가능합니다.
  Docker 환경에서 stdout은 docker logs로 누구나 볼 수 있습니다. logging 모듈로
  전환하면 프로덕션에서 DEBUG/INFO 레벨 메시지를 숨기고, WARNING 이상만 출력할
  수 있습니다. 또한 토큰이나 PHI를 로깅하지 않는 규칙을 적용하면, 로그가
  유출되어도 민감 정보가 포함되지 않습니다.

  단계별 구현:
  1. routes_surveys.py 상단에 import logging; logger = logging.getLogger(__name__) 추가
  2. 모든 print() 문을 logger.debug() 또는 logger.info()로 교체
  3. REDCap 토큰 출력 코드(1188행) 완전히 제거하거나 마스킹
  4. 환자 설문 답변 전체 출력(798-808행) 제거
  5. 앱 시작 시 로그 레벨 설정: logging.basicConfig(level=logging.WARNING)
  6. routes_transcript.py, nlp_service.py의 print()도 동일하게 마이그레이션

  코드 — 수정 전 (취약):
    # routes_surveys.py:1188 — REDCap 토큰 노출
    print(f"[CONFIG] Token: {REDCAP_API_TOKEN[:8]}...{REDCAP_API_TOKEN[-4:]}")

    # routes_surveys.py:798-808 — 환자 설문 응답 전체 출력
    print(f"[SPEAKER] {submission.speaker}")
    print(json.dumps(submission.answers, indent=2, ensure_ascii=False))

  코드 — 수정 후 (안전):
    import logging
    logger = logging.getLogger(__name__)

    # REDCap 토큰 — 마스킹 또는 제거
    logger.debug("[CONFIG] REDCap token configured: %s", "***" * 4)
    # 토큰 값 자체는 절대 로깅하지 않음

    # 환자 설문 응답 — 식별자만 로깅, 내용 제거
    logger.info("Survey submitted: speaker=%s, type=%s",
                submission.speaker, submission.survey_type)
    # submission.answers 전체를 로깅하지 않음

    # 앱 시작 시 로그 레벨 설정 (main.py 또는 앱 초기화)
    import logging
    log_level = os.getenv("LOG_LEVEL", "WARNING")
    logging.basicConfig(
        level=getattr(logging, log_level),
        format="%(asctime)s %(name)s %(levelname)s %(message)s"
    )

    # API 토큰 마스킹 유틸리티
    def mask_token(token: str) -> str:
        """토큰의 첫 4자만 표시, 나머지는 마스킹."""
        if len(token) <= 4:
            return "****"
        return token[:4] + "*" * (len(token) - 4)

  우선순위 & 소요 시간: 중간 — PHI와 인증정보 노출 방지 | 1-2시간
  의존성: 없음 (독립적으로 수정 가능)

■ 이 프로젝트에 미치는 실제 영향

  - 로그의 REDCap API 토큰으로 우리 애플리케이션을 우회하여
    직접 Cedars-Sinai REDCap 데이터베이스에 접근/수정 가능
  - 로그에 보이는 환자 설문 응답은 PHI 노출에 해당
  - 공유 개발 환경에서 다른 개발자가 접근해선 안 되는 환자 데이터를 볼 수 있음

■ 실제 테스트 결과 (2026-02-20)

취약점 8: 기본 API 키 폴백
심각도: 높음 | OWASP: A07 식별 및 인증 실패
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 쉬운 설명 (비유)

  금고를 사면 초기 비밀번호가 "1234"로 설정되어 있습니다. 설명서에
  "이 비밀번호를 변경하세요"라고 쓰여 있고, 대부분 변경합니다.
  하지만 누군가 변경을 잊으면, 설명서를 읽은 누구나 비밀번호를 알고 있습니다.

  우리 코드: API_KEY = os.getenv("API_KEY", "default-dev-key")
  이 뜻은: "환경변수에서 API_KEY를 사용하고, 설정되지 않으면
  'default-dev-key'를 사용." "default-dev-key" 문자열은 GitHub의
  소스 코드에서 볼 수 있습니다. .env 파일이 없거나 변수가 미설정이면,
  서버는 조용히 이 잘 알려진 기본값을 사용합니다.

■ 취약 코드 (2곳)

  routes_transcript.py:73
    _API_KEY = os.getenv("API_KEY", "default-dev-key")

  routes_nlp.py:37
    _API_KEY = os.getenv("API_KEY", "default-dev-key")

■ 문제

  API_KEY 환경변수가 누락되면 서버가 "default-dev-key"를 유효한 API 키로 수락.
  이 문자열은 소스 코드(GitHub)에 공개되어 있음.

■ 공격 시나리오 M — 기본 키로 접근

  .env 파일이 없거나 API_KEY가 설정되지 않은 경우:

    curl -H "X-API-Key: default-dev-key" \
         http://target:8000/api/transcript/predictions/sid-01
    → 200 OK, 전체 환자 데이터 반환

■ 수정 방법

  기본값 제거. API_KEY 미설정 시 시작 시 오류 발생:

    _API_KEY = os.getenv("API_KEY")
    if not _API_KEY:
        raise RuntimeError("API_KEY environment variable must be set")

■ 상세 수정 가이드

  이 수정이 효과적인 이유:
  os.getenv("API_KEY", "default-dev-key")는 환경변수가 미설정일 때 기본값을
  사용합니다. 이 기본값은 소스 코드(GitHub)에 공개되어 있으므로 누구나 알 수
  있습니다. .env 파일이 누락되거나 API_KEY가 실수로 삭제되면, 서버는 조용히
  이 잘 알려진 기본값으로 작동하여 전체 API가 노출됩니다. os.environ["API_KEY"]
  를 사용하면 환경변수가 없을 때 즉시 오류가 발생하여, 안전하지 않은 상태로
  서버가 시작되는 것을 원천 차단합니다. "안전하게 실패(fail secure)" 원칙입니다.

  단계별 구현:
  1. routes_transcript.py:73 에서 os.getenv("API_KEY", "default-dev-key")를
     os.environ["API_KEY"]로 변경
  2. routes_nlp.py:37 에서 동일하게 변경
  3. 서버 시작 시 API_KEY 환경변수 존재 확인 로직 추가
  4. .env.example에 API_KEY=CHANGE_ME 가 있는지 확인

  코드 — 수정 전 (취약):
    # routes_transcript.py:73 (routes_nlp.py:37도 동일)
    _API_KEY = os.getenv("API_KEY", "default-dev-key")
    # 위험: .env 없으면 "default-dev-key"가 유효한 API 키가 됨
    # "default-dev-key"는 GitHub에 공개된 소스 코드에서 확인 가능

  코드 — 수정 후 (안전):
    # routes_transcript.py:73 (routes_nlp.py:37도 동일)
    _API_KEY = os.environ["API_KEY"]
    # API_KEY 미설정 시 KeyError → 서버 시작 실패 (안전한 실패)

    # 또는 더 명확한 오류 메시지를 원하면:
    _API_KEY = os.getenv("API_KEY")
    if not _API_KEY:
        raise RuntimeError(
            "API_KEY environment variable must be set. "
            "Copy .env.example to .env and set a secure API key."
        )

  우선순위 & 소요 시간: 높음 — 단 5분 수정으로 심각한 위험 제거 | 5분
  의존성: 없음 (독립적으로 수정 가능). .env 파일에 API_KEY가 설정되어 있는지 확인 필요

■ 이 프로젝트에 미치는 실제 영향

  - 현재는 악용 불가 (.env 파일에 실제 API 키가 설정됨)
  - 하지만 누군가 .env 없이 서버를 배포하거나 API_KEY 줄이 실수로
    삭제되면, "default-dev-key"로 전체 환자 데이터에 접근 가능
  - 이 키는 소스 코드를 읽은 누구나 알 수 있음

■ 실제 테스트 결과 (2026-02-20)

  "default-dev-key" → HTTP 403 (현재 차단됨 — .env에 실제 API_KEY 설정)
  빈 문자열 키 → HTTP 403 (누락)
  실제 키 → HTTP 200 (정상 작동)

  취약점은 코드에 존재하지만 현재는 악용 불가 (.env가 API_KEY 설정).
  위험: .env가 없거나 API_KEY 미설정 시, 소스 코드에 공개된
  "default-dev-key"로 전체 API 접근 가능.

취약점 9: Nginx 보안 헤더 비활성화
심각도: 중간 | OWASP: A05 보안 설정 오류
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 쉬운 설명 (비유)

  보안 카메라, 화재 경보기, 창문 잠금장치가 없는 건물을 상상해보세요.
  이것들 자체가 직접적인 위협은 아니지만, 건물을 침입에 훨씬 취약하게
  만들고, 문제가 발생했을 때 감지하기 훨씬 어렵게 합니다.

  웹 브라우저에는 서버가 특별한 응답 헤더를 보내면 활성화되는 보안
  기능이 내장되어 있습니다:
  - "X-Frame-Options: DENY": 다른 웹사이트가 내 페이지를 감싸는 것 방지 (클릭재킹 방지)
  - "Content-Security-Policy": 내 서버가 아닌 JavaScript 실행 차단 (XSS 방지)
  - "server_tokens off": 서버 소프트웨어 버전 숨김 (알려진 취약점 검색 방지)

  우리 Nginx는 이런 보호 없이 설정되어 있습니다. 적절한 설정이 파일에
  존재하지만 주석 처리되어(비활성화) 있습니다.

■ 현재 설정 (활성 — nginx default.conf 93-127행)

  보안 헤더 없음, 레이트 제한 없음, server_tokens off 없음.

■ 주석 처리된 설정 (1-85행 — 적절한 보안 포함)

  적절한 보안 설정이 존재하지만 주석 처리됨:
    # add_header X-Content-Type-Options nosniff always;
    # add_header X-Frame-Options DENY always;
    # add_header X-XSS-Protection "1; mode=block" always;
    # server_tokens off;
    # limit_req zone=api_limit burst=20 nodelay;

■ 누락된 보호

  1) X-Content-Type-Options: nosniff — MIME 타입 스니핑 방지
  2) X-Frame-Options: DENY — 클릭재킹 방지
  3) X-XSS-Protection — 브라우저 XSS 필터 활성화
  4) Referrer-Policy — 리퍼러 헤더 유출 제어
  5) server_tokens off — Nginx 버전 숨김
  6) 레이트 제한 — 무차별 대입/DoS 방지

■ 수정 방법

  보안 강화된 nginx 설정(1-85행)을 주석 해제.

■ 상세 수정 가이드

  이 수정이 효과적인 이유:
  보안 헤더는 브라우저에게 보안 정책을 알려주는 지시입니다. 이 헤더 없이는
  브라우저가 기본 동작을 하여 다양한 공격에 취약해집니다. 각 헤더는 특정
  공격 유형을 차단합니다. 이미 적절한 설정이 nginx.conf에 주석으로 존재하므로
  주석 해제만 하면 됩니다. 즉각적인 보안 향상을 얻을 수 있습니다.

  단계별 구현:
  1. nginx default.conf 파일 열기
  2. 주석 처리된 보안 설정 블록(1-85행) 주석 해제
  3. 현재 활성 블록(93-127행)을 보안 강화 블록으로 교체
  4. docker compose restart nginx 로 적용
  5. 브라우저 DevTools에서 응답 헤더 확인

  코드 — 수정 전 (취약):
    # nginx default.conf — 현재 활성 설정 (보안 헤더 없음)
    server {
        listen 80;
        server_name _;
        # 보안 헤더 전혀 없음
        # server_tokens 켜져 있음 (Nginx 버전 노출)
    }

  코드 — 수정 후 (안전):
    # nginx default.conf — 7개 보안 헤더 + server_tokens off
    server_tokens off;    # Nginx 버전 숨김 — 알려진 취약점 검색 방지

    server {
        listen 80;
        server_name _;

        # 1. MIME 타입 스니핑 방지 — 브라우저가 Content-Type을 추측하지 않도록
        #    방지: 악성 파일을 다른 MIME 타입으로 실행하는 공격
        add_header X-Content-Type-Options nosniff always;

        # 2. 클릭재킹 방지 — 다른 사이트가 iframe으로 우리 페이지를 감싸지 못하도록
        #    방지: 투명 iframe 위에 클릭을 유도하는 공격
        add_header X-Frame-Options DENY always;

        # 3. 브라우저 XSS 필터 — 반사형 XSS 차단 (레거시 브라우저 지원)
        #    방지: URL에 삽입된 스크립트 실행
        add_header X-XSS-Protection "1; mode=block" always;

        # 4. Content Security Policy — 인라인 스크립트 및 외부 리소스 차단
        #    방지: XSS, 데이터 인젝션, 악성 외부 스크립트 로딩
        add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self';" always;

        # 5. 리퍼러 정책 — 다른 사이트로 이동 시 URL 유출 제어
        #    방지: 환자 ID 등이 포함된 URL이 외부 사이트에 전달
        add_header Referrer-Policy "strict-origin-when-cross-origin" always;

        # 6. HSTS — HTTPS 강제 (HTTPS 설정 후 활성화)
        #    방지: SSL 스트리핑 공격 (HTTPS→HTTP 다운그레이드)
        # add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

        # 7. 권한 정책 — 불필요한 브라우저 기능 비활성화
        #    방지: 카메라, 마이크, 위치 정보 무단 접근
        add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
    }

■ 쉬운 설명 (비유)

  건물 로비에 보안 시스템의 완전한 설계도를 게시하는 것을 상상해보세요 —

  FastAPI는 모든 엔드포인트, 모든 파라미터, 모든 예상 형식을 보여주고

  (Swagger UI)를 자동 생성합니다. 개발 중에는 매우 유용하지만,
  프로덕션에서는 공격자에게 시스템의 완전한 지도를 제공하므로 위험합니다.

■ 현재 상태

  FastAPI가 다음 주소에서 대화형 API 문서를 자동 생성:
  - http://localhost:8000/docs   (Swagger UI)
  - http://localhost:8000/redoc  (ReDoc)

  인증 없이 접근 가능.

■ 문제

  Swagger UI는 다음을 제공:
  - 모든 API 엔드포인트의 완전한 목록
  - 요청/응답 스키마
  - 대화형 "Try it out" 기능 (API 호출 실행 가능)

  공격자에게 API 공격 표면의 완전한 지도를 제공.

■ 공격 시나리오 N — API 정찰

    app = FastAPI(docs_url=None, redoc_url=None)

■ 상세 수정 가이드

  이 수정이 효과적인 이유:
  FastAPI의 Swagger UI와 ReDoc은 모든 API 엔드포인트, 파라미터, 요청/응답
  스키마를 대화형으로 보여줍니다. 공격자에게 시스템의 완전한 지도를 제공하는
  것과 같습니다. 프로덕션에서 docs_url=None과 redoc_url=None을 설정하면
  이 문서 페이지가 비활성화되어 공격자의 API 정찰을 차단합니다. 환경변수로
  토글하면 개발 중에는 편리하게 사용하고 프로덕션에서만 비활성화할 수 있습니다.

  단계별 구현:
  1. .env 파일에 DEBUG=false 환경변수 추가 (프로덕션)
  2. FastAPI 앱 초기화에서 환경변수 기반으로 docs URL 토글
  3. /openapi.json 엔드포인트도 함께 비활성화
  4. docker-compose.yml에서 DEBUG 환경변수 설정

  코드 — 수정 전 (취약):
    # main.py 또는 앱 초기화 파일
    app = FastAPI(
        title="Prostate Cancer Doctor-Patient Conversation Archive API",
        version="1.0.0"
    )
    # /docs, /redoc, /openapi.json 모두 인증 없이 접근 가능

  코드 — 수정 후 (안전):
    import os

    DEBUG = os.getenv("DEBUG", "false").lower() == "true"

    app = FastAPI(
        title="Prostate Cancer Doctor-Patient Conversation Archive API",
        version="1.0.0",
        docs_url="/docs" if DEBUG else None,
        redoc_url="/redoc" if DEBUG else None,
        openapi_url="/openapi.json" if DEBUG else None
    )

    # docker-compose.yml
    backend:
      environment:
        - DEBUG=${DEBUG:-false}       # 프로덕션: false
    # 개발 환경 .env:
    # DEBUG=true

  의존성: 없음 (독립적으로 수정 가능)

심각도: 높음 | OWASP: A07 식별 및 인증 실패
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 쉬운 설명 (비유)

  경보 패널에 경보 코드가 적힌 포스트잇을 붙여놓은 것을 상상해보세요.
  방문객, 배달원, 침입자를 포함하여 건물에 들어오는 누구나 경보 코드를
  볼 수 있습니다.

  Next.js(우리 웹 프레임워크)에는 규칙이 있습니다: "NEXT_PUBLIC_"으로
  시작하는 환경변수는 사용자 브라우저에서 실행되는 JavaScript 코드에
  직접 포함됩니다. docker-compose.yml에 "NEXT_PUBLIC_API_KEY"가
  설정되어 있으므로, 실제 API 키가 모든 방문자의 브라우저가 다운로드하는
  JavaScript 파일에 나타납니다.

  웹 대시보드를 열고, 브라우저 개발자 도구를 열고, "sk_live"를 검색하면
  전체 API 키를 찾을 수 있습니다. 이 키로 어떤 환자의 데이터든 직접
  API 호출이 가능합니다.

■ 취약 코드

  docker-compose.yml:109
    NEXT_PUBLIC_API_KEY: ${API_KEY}

■ 문제

  Next.js 규칙: NEXT_PUBLIC_ 접두사가 붙은 환경변수는
  클라이언트 측 JavaScript 번들에 포함됨.

  이는 API 키가:
  1) 브라우저 페이지 소스/DevTools에서 확인 가능
  2) 다운로드 가능한 JavaScript 번들에 포함
  3) 웹 애플리케이션을 방문하는 모든 사용자가 접근 가능

■ 공격 시나리오 O — 브라우저 소스에서 키 추출

  1. 브라우저에서 http://localhost:3000 열기
  2. DevTools → Sources → "sk_live" 또는 "API_KEY" 검색
  3. 또는: curl http://localhost:3000/_next/static/chunks/*.js | grep -o 'sk_[a-z0-9]*'
  → 클라이언트 측 코드에서 API 키 발견

  추출된 키로 취약점 1, 2, 3, 5의 모든 공격 가능.

■ 수정 방법

  [옵션 A] Backend-for-Frontend(BFF) 패턴
  [옵션 B] NEXT_PUBLIC_ 접두사 제거, Next.js API 라우트로 서버 측 프록시

■ 상세 수정 가이드

  이 수정이 효과적인 이유:
  Next.js에서 NEXT_PUBLIC_ 접두사가 붙은 환경변수는 빌드 시 클라이언트
  JavaScript 번들에 직접 삽입됩니다. 이는 webpack이 process.env.NEXT_PUBLIC_*
  참조를 실제 값으로 치환하기 때문입니다. 따라서 브라우저 DevTools나 JS 파일
  다운로드로 누구나 API 키를 추출할 수 있습니다. NEXT_PUBLIC_ 접두사를 제거하고
  서버사이드 프록시(Next.js API Route)를 사용하면, API 키는 서버에만 존재하고
  브라우저에는 절대 노출되지 않습니다.

  단계별 구현:
  1. docker-compose.yml에서 NEXT_PUBLIC_API_KEY를 API_KEY로 변경
     (NEXT_PUBLIC_ 접두사 제거)
  2. Next.js app/api/proxy/[...path]/route.ts 서버사이드 프록시 API Route 생성
  3. 프록시 라우트에서 서버 측 환경변수로 API 키를 백엔드에 전달
  4. 프론트엔드 API 호출을 백엔드 직접 호출에서 프록시 경유로 변경
  5. .env에서 NEXT_PUBLIC_API_KEY 변수명을 API_KEY로 변경

  코드 — 수정 전 (취약):
    # docker-compose.yml:109
    webapp:
      environment:
        - NEXT_PUBLIC_API_KEY=${API_KEY}   # 브라우저 JS에 포함됨!

    # 프론트엔드 코드 (React 컴포넌트)
    const API_KEY = process.env.NEXT_PUBLIC_API_KEY;  // 빌드 시 실제 값으로 치환
    fetch("http://backend:8000/api/transcript/analyze", {
        headers: { "X-API-Key": API_KEY }  // 브라우저에서 키 노출
    });

  코드 — 수정 후 (안전):
    # docker-compose.yml — NEXT_PUBLIC_ 접두사 제거
    webapp:
      environment:
        - API_KEY=${API_KEY}   # 서버 사이드에서만 접근 가능

    # Next.js API Route (app/api/proxy/[...path]/route.ts)
    // 서버사이드 프록시 — API 키가 서버에만 존재
    import { NextRequest, NextResponse } from 'next/server';

    const BACKEND_URL = process.env.BACKEND_URL || 'http://backend:8000';
    const API_KEY = process.env.API_KEY;  // 서버 측 환경변수

    export async function GET(req: NextRequest, { params }: { params: { path: string[] } }) {
        const backendPath = params.path.join('/');
        const response = await fetch(`${BACKEND_URL}/api/${backendPath}`, {
            headers: { 'X-API-Key': API_KEY || '' }  // 서버가 키를 추가
        });
        const data = await response.json();
        return NextResponse.json(data);
    }

    # 프론트엔드 코드 (React 컴포넌트) — 키 없이 프록시 호출
    fetch("/api/proxy/transcript/analyze", {
        // X-API-Key 헤더 불필요 — 프록시가 서버 측에서 추가
    });

  우선순위 & 소요 시간: 높음 — 현재 웹 방문자 누구나 API 키 추출 가능 | 1-2시간
  의존성: 없음 (독립적으로 수정 가능). 취약점 2(JWT 마이그레이션) 완료 후에는 프록시가 JWT 토큰을 관리하도록 확장 가능

  webapp(React)에서 렌더링 시 다음 경우 실행 가능:
  - dangerouslySetInnerHTML 사용 시
  - href 또는 이벤트 핸들러 속성에 데이터 삽입 시

  취약점 6(설문 무인증)과 결합하면, 익명 사용자가 의사가 대시보드를
  볼 때 실행되는 저장형 XSS를 심을 수 있음.

■ 수정 방법

  [즉시] 저장 전 모든 문자열 입력 새니타이징:
    import bleach
    clean_text = bleach.clean(raw_text)

  [중기] Content Security Policy 헤더 (취약점 9 참조)로 인라인 스크립트 차단.
  [최선] React는 기본적으로 JSX를 자동 이스케이프 — 사용자 데이터에
  dangerouslySetInnerHTML이 사용되지 않는지 확인.

■ 상세 수정 가이드

  이 수정이 효과적인 이유:
  저장형 XSS는 악성 스크립트가 데이터베이스에 저장된 후 다른 사용자의
  브라우저에서 실행되는 공격입니다. 입력 새니타이징(bleach.clean)은 저장
  시점에서 HTML/JS 태그를 제거하여 근본 원인을 차단합니다. CSP 헤더는
  새니타이징을 우회하더라도 브라우저가 인라인 스크립트를 실행하지 않도록
  하는 2차 방어선입니다. 두 가지를 함께 사용하면 다층 방어가 됩니다.

  단계별 구현:
  1. bleach 패키지 설치: requirements.txt에 bleach 추가 후 pip install bleach
  2. routes_surveys.py 상단에 import bleach 추가
  3. 새니타이징 유틸리티 함수 작성
  4. /api/surveys/submit 엔드포인트에서 speaker, patient_id, file, survey_type,
     answers 모든 문자열 필드에 새니타이징 적용
  5. Nginx 또는 FastAPI 미들웨어에 CSP 헤더 추가
  6. Webapp(React) 코드에서 dangerouslySetInnerHTML 사용 여부 검색 및 제거

  코드 — 수정 전 (취약):
    # routes_surveys.py - /api/surveys/submit

    async def submit_survey(submission: SurveySubmission):

            speaker=submission.speaker,           # <img src=x onerror=alert(1)>
            patient_id=submission.patient_id,      # <script>alert(1)</script>

  코드 — 수정 후 (안전):
    import bleach

    def sanitize_string(value: str) -> str:
        """HTML 태그와 스크립트를 제거하여 XSS 방지."""
        return bleach.clean(value, tags=[], attributes={}, strip=True)

    def sanitize_dict(data: dict) -> dict:
        """딕셔너리 내 모든 문자열 값을 새니타이징."""
        return {k: sanitize_string(v) if isinstance(v, str) else v
                for k, v in data.items()}

    @router.post("/submit")
    async def submit_survey(submission: SurveySubmission):
        new_record = SurveySubmissionLog(
            speaker=sanitize_string(submission.speaker),
            patient_id=sanitize_string(submission.patient_id),
            answers=json.dumps(sanitize_dict(submission.answers))
        )
        db.add(new_record)

    # Nginx CSP 헤더 (default.conf):
    add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';" always;

  우선순위 & 소요 시간: 높음 — 설문 무인증(취약점 6)과 결합 시 즉시 악용 가능 | 1-2시간
  의존성: 취약점 6(설문 인증)을 먼저 수정하면 익명 공격은 차단되지만, 인증된 사용자의 XSS도 방지해야 하므로 새니타이징은 독립적으로 필요

■ 이 프로젝트에 미치는 실제 영향

  3. 숨겨진 코드가 의사의 브라우저에서 실행되어 세션 탈취

개요:
  단일 공유 API 키 → 4가지 인증 모듈 + 환자별 접근 제어 시스템 구현.
  AUTH_MODE 환경변수로 전환 가능. 기존 방식(api_key)이 기본값으로 하위 호환 유지.

4가지 인증 모듈:
  A. api_key (기본값) — 기존 단일 X-API-Key. superuser로 동작, 접근 제어 우회. DB 불필요.
  B. multi_key — 사용자별 고유 API 키. SHA-256 해시로 DB 저장. X-API-Key 헤더 유지.
  C. jwt — 로그인(POST /api/auth/login) → JWT 토큰 → Authorization: Bearer 인증.
  D. oauth2 — Google/Okta/Azure AD 외부 IdP 연동. OIDC/JWKS 검증. 자동 사용자 생성.

신규 파일 (12개):
  auth/__init__.py          — get_current_user FastAPI 의존성
  auth/base.py              — AuthUser dataclass + AuthBackend Protocol
  auth/registry.py          — AUTH_MODE → 백엔드 선택 (lru_cache)
  auth/access_control.py    — check_patient_access() + get_accessible_patient_ids()
  auth/models.py            — AuthUser, AuthAPIKey, PatientAccess (SQLAlchemy 모델)
  auth/schemas.py           — Pydantic 요청/응답 모델
  auth/admin_routes.py      — 관리 API: 사용자/키/환자접근/로그인/me/mode
  auth/backends/__init__.py — 패키지 init
  auth/backends/api_key.py  — 모듈 A: 기존 단일 API 키
  auth/backends/multi_key.py — 모듈 B: 사용자별 API 키
  auth/backends/jwt_auth.py — 모듈 C: JWT Bearer 토큰
  auth/backends/oauth2.py   — 모듈 D: OAuth2 외부 IdP
