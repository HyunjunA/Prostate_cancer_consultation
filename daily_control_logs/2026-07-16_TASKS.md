### Evidence 1 — false negative (PHI missed) ⚠️ serious

```

file B, row 99  : "...my regular guy, Dr. [Name], on the 25th..."
                  → only 'on the 25th' became [Date]; Dr. [Name] was left in place  ❌ missed
```

```
                                                      clinical, not PHI
```

→ The prompt explicitly says *"Do NOT mark … visit counts, or ordinary non-identifier
numbers"*, and gpt-4o broke it.

## Progress as of 2026-07-16

### 1) Understanding the tool — ✅ done

- `PHI_Removal` is a **two-stage body-text PHI detector**: (i) a local BERT screener
  (high recall, flags rows) → (ii) an LLM adjudicator (extracts the real PHI spans and
  categories)
- Trained on 50 transcripts (40 train / 10 validation), targeting **names, dates, and
  phone numbers in the body text**, not just numeric identifiers
- Explanatory documents written: `docs/PHI_Removal_Overview.pdf` (English) and its
  Korean counterpart
- **Verified against real input files** — `scripts/check_phi_removal.py`
  - A 123-row transcript → stage 1 flagged 16 rows → stage 2 extracted Name/Date from a
    `"Dr. [Name], on the 25th"` construction and rejected ordinary conversation as PHI = 0
  - The original package is **unmodified** (import plus runtime override)

### 2) Adding hashing — 🔄 plan complete (direction corrected), implementation pending

- **The hashing itself is already production-grade**: affine (test) → **AES-SIV**
  throughout, with end-to-end verification (commits `8ed2466` and `0ba76e8`; upload →
  AES de-identification → pipeline → DB (Base32) → survey re-identification `SID_22` →
  successful REDCap push)
- ⚠️ **Direction corrected**: "add the hashing **there**" plus "**before uploading**"
  means **one integrated tool that runs on the coordinator's PC, before upload**.
  → PHI never reaches the server at all (consistent with the 7/10 log's principle that
  the server side must hold no PHI).
  → **The earlier "integrate on the server" design is abandoned.** The current admin
  upload's **server-side de-identification path (path 2)** also conflicts with this
  policy → a decision on how to handle it is needed.
- **New design**: `[coordinator's PC] original → integrated tool ((i) PHI_Removal body
  cleaning + (ii) AES hashing) → only the clean file is uploaded → [server] stored as
  is → watch → pipeline`
  - Plan document: `docs/PHI_Removal_Integration_Plan.pdf` (corrected edition)
  - Side benefit: **the server gets simpler** — torch, transformers, PHI_Removal, and
    `input_phi_removed` all become unnecessary
- **Core work remaining**: the span → `[Category]` **substitution logic**, and **binding
  the two capabilities into one tool** (the bridge is already proven in
  `check_phi_removal.py`)
