### ★★ Top priority — treat the side-effect domains (ED, incontinence, irritative symptoms) as "one designated treatment" ⬜ to do

> **This is the settled policy.**
> **Decided at the 2026-06-02 meeting** (source: `2026-06-02_webapp_feedback.md`,
> items A-3 and A-4 — lead developer and collaborator feedback).

**Background**: the same side effect carries different risk per treatment, so scores
and supporting sentences come out **per treatment** (surgery / radiation / ablation)
— ED surgery 4, radiation 3, ablation 2, for example. The lead developer's question
was *"then how would you score it?"* — asking about every treatment makes risk
perception impossible to score as **a single outcome**, which breaks the statistical
analysis.

**Decision — ask and score using only the single most relevant treatment per side
effect**:

- Erectile dysfunction (ed) → **radical prostatectomy**
- Urinary incontinence (inc) → **radical prostatectomy**
- Irritative / lower urinary tract symptoms (ius) → **radiation**
- Selection rule: the treatment where that side effect is **most pronounced** (surgery
  for ED and incontinence, radiation for irritative symptoms)
- **Name the assumed treatment in the question text** (e.g. "if you were to have a
  radical prostatectomy…")

**Cross-check (verification action)**: confirm once more that the wording on screen
is the latest version reflecting this decision — the lead developer and collaborator
had already aligned it, but double-check.

**A-4 — side-effect display test**: the supporting sentence count varies **from one
to four** because of the per-treatment estimates → the UI must display consistently
**regardless of count**, without breaking the layout. Test 1, 2, 3, and 4; no
fixed-width display cells.

**Related (physician scores)**: aligning the physician-side side-effect scores to the
same **single designated treatment** keeps them consistent with the survey outcome.

**✅ Implemented 2026-06-26** — both sides now use the designated treatment:

### 1-0. ★ Top priority — inconsistent overall score (no single source of truth) ✅ resolved (backend unified and verified)

> **Symptom**: the same patient's "overall score" differed by screen.
> Measured: trajectory (individual) **2.4** vs Patient Reports **2.6** vs Summary **2.73**.

**Resolution (2026-06-25)**: all three endpoints now follow one rule —
**MAX(ai_score) per domain → missing domains count as 0 → average over five domains**
(the rule `/scores/average` already used, matching the documented intent and the documented backend
rule 5).

- Added the shared helper `_overall_from_domain_maxes()` in `routes_doctor.py`
- `/scores/trajectory`: **"last row" per domain (a non-deterministic bug — no ORDER BY)
  → MAX**, and the per-patient overall now uses the five-domain average
- `/scores/summary`: overall changed from **an average over all evidence rows → the
  five-domain average of domain MAXes** (the `by_class` detail is unchanged)
- **Verified**: all six files agree across the three endpoints (SID 21 → **2.6**;
  already-consistent files such as SID 14 = 3.6 and SID 33 = 4.0 are unchanged);
  `pytest tests/test_doctor_endpoints.py` 37 passed
- **Follow-up**: the pipeline's `ai_overall_score` in the AI repo's
  `db/persistence_helper.py` (average over all rows) should adopt the same rule —
  **affects new runs only**, and does not change what the dashboard displays

**Root cause (corrected)** — all three endpoints read **the same table**,
`llm_domain_scoring_and_summary` (LLM `ai_score`). The problem was that this table
holds several rows per (file, domain) — one per treatment for the side-effect domains
— and each endpoint aggregated differently:

1. ~~Different source tables~~ → **corrected: the same table.** Patient Reports
   (`/scores/average`) used the per-domain MAX, trajectory used the last row
   (non-deterministic), summary used the average over all rows.
2. **The same domain scored differently** — for ed and inc, NLP-MAX = **4** versus
   LLM = **3**.
3. **Missing domains handled differently** — Patient Reports pads with 0 and divides
   by 5 (`routes_doctor.py:611–632`); trajectory divides by the number of present
   domains (`:846`).
4. **Different aggregation units** — a five-domain average versus a **per-sentence
   average** (summary overall, count 11 → 2.73, `:750`).
5. **Different row selection when a domain has several LLM rows** — trajectory
   individual 2.4 versus summary `by_class` average 2.2, from the same LLM source,
   because of max/last/representative-sentence differences.

**Related files**: `app/Backend/routes_doctor.py` (`/scores/average` from ~525,
`/scores/trajectory` from ~767, `/scores/summary` around 750), and the frontend
`PhysicianReportsModifiedV41Timothy.tsx` (Patient Reports `overallScore` at `:4652`,
trajectory `chartData` at `:2318`; the breakdown and rubric-report domain scores also
read `scoreAverage.data` and are therefore affected).

**Note**: the documented backend rule 5 says scores come from
`llm_domain_scoring_and_summary` (`ai_score`), so `/scores/average` — used by Patient
Reports, the breakdown, and the rubric report — was violating the rule by using the
NLP MAX. The per-domain scores in the new rubric report could therefore show values
that differ from the LLM.

**Decisions needed before further changes**: (1) single source = LLM `ai_score` or
NLP MAX evidence, (2) missing domains = pad with 0 and divide by 5, or divide by the
number present, (3) domain average versus sentence average.
