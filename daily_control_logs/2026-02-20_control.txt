Vulnerability 1: Path Traversal (patient_id)
Severity: HIGH | OWASP: A01 Broken Access Control
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ What This Means (Plain Language)

  Imagine a library where you request a book by shelf number: "Give me the
  book on shelf 3." But instead, someone requests: "Go to shelf 3, then
  walk out of the library, into the office next door, and bring me the
  security guard's keys." The librarian follows the directions blindly
  because nobody told them to check if the destination is still inside
  the library.

  In our system, when you request a patient's file (e.g., "sid-01"), the
  server builds a file path: /app/uploads/sid-01_predictions.xlsx. But if
  someone sends "../../etc/passwd" as the patient ID, the server builds:
  /app/uploads/../../etc/passwd_predictions.xlsx, which resolves to
  /etc/passwd_predictions.xlsx — a location OUTSIDE the uploads folder.

■ Real-World Impact on This Project

  An attacker could:
  - READ files outside the uploads directory (e.g., configuration files
    containing database passwords or API tokens)
  - WRITE files anywhere in the container (e.g., overwrite application
    code with malicious code, plant a backdoor that runs every time
    the server starts)
  - In the worst case, gain full control of the Docker container

■ Fix

  import re
  _PATIENT_ID_PATTERN = re.compile(r'^[a-zA-Z0-9][a-zA-Z0-9_-]{0,254}$')

  def _validate_patient_id(patient_id: str) -> str:
      if not _PATIENT_ID_PATTERN.match(patient_id):
          raise HTTPException(400, "Invalid patient_id format")
      resolved = (_UPLOAD_DIR / f"{patient_id}_predictions.xlsx").resolve()
      if not str(resolved).startswith(str(_UPLOAD_DIR.resolve())):
          raise HTTPException(400, "Invalid patient_id")
      return patient_id

■ Detailed Fix Guide

  WHY THIS FIX WORKS:
  This fix uses defense-in-depth with TWO independent validation layers:

  Layer 1 (regex whitelist): The regex ^[a-zA-Z0-9][a-zA-Z0-9_-]{0,254}$
  only allows alphanumeric characters, hyphens, and underscores. It
  explicitly REJECTS dots (.), slashes (/), backslashes (\), percent signs
  (%), and all other special characters. This means "../" and "..%2F" and
  every other traversal sequence is blocked at the character level. The
  patient_id "../../etc/passwd" fails because it contains dots and slashes.

  Layer 2 (resolve() check): Even if a future code change weakens the
  regex (e.g., allowing dots for IDs like "patient-1.2"), the resolve()
  check catches any traversal. Path.resolve() converts the path to its
  absolute canonical form (resolving all ../ sequences), then we verify
  the resolved path still starts with the uploads directory. If someone
  crafts an ID that passes the regex but still escapes the directory, this
  second check catches it.

  Both layers together mean an attacker must bypass TWO independent
  mechanisms — if either one works, the attack fails.

  STEP-BY-STEP:
  1. Open routes_transcript.py
  2. Add the _PATIENT_ID_PATTERN regex constant near the top of the file,
     close to the existing _UPLOAD_DIR constant (around line 411)
  3. Add the _validate_patient_id() function immediately after
  4. Call _validate_patient_id(patient_id) at the START of every function
     that accepts a patient_id parameter:
     - _xlsx_path() — add validation before building the path
     - _save_xlsx() — add validation before writing
     - download endpoint (line 162)
     - download-batch endpoint (line 319, in the loop over patient_ids)
     - history endpoint (line 498)
     - predictions endpoint (line 562)
  5. Rebuild the backend container
  6. Test with valid ID: GET /download/sid-01 → should still return 200
  7. Test with traversal: GET /download/../../etc/passwd → should return 400

    import re
    from pathlib import Path

    _UPLOAD_DIR = Path("/app/uploads")
    _PATIENT_ID_PATTERN = re.compile(r'^[a-zA-Z0-9][a-zA-Z0-9_-]{0,254}$')

    def _validate_patient_id(patient_id: str) -> str:
        """Validate patient_id against path traversal attacks.

        Uses defense-in-depth:
        1. Regex whitelist — blocks special characters (../ etc.)
        2. Resolve check — verifies path stays inside uploads directory
        """
        # Layer 1: Reject any characters not in the whitelist
        if not _PATIENT_ID_PATTERN.match(patient_id):
            raise HTTPException(
                status_code=400,
                detail="Invalid patient_id format",
            )
        # Layer 2: Verify resolved path is under _UPLOAD_DIR
        resolved = (_UPLOAD_DIR / f"{patient_id}_predictions.xlsx").resolve()
        if not str(resolved).startswith(str(_UPLOAD_DIR.resolve())):
            raise HTTPException(
                status_code=400,
                detail="Invalid patient_id",
            )
        return patient_id

    def _xlsx_path(patient_id: str) -> Path:
        _validate_patient_id(patient_id)  # Validate BEFORE building path
        return _UPLOAD_DIR / f"{patient_id}_predictions.xlsx"

        _UPLOAD_DIR.mkdir(parents=True, exist_ok=True)
        _xlsx_path(patient_id).write_bytes(xlsx_bytes)

        ...

Vulnerability 2: Authentication — Timing Attack + Shared Key
Severity: MEDIUM | OWASP: A07 Identification and Authentication Failures
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ What This Means (Plain Language)

  Imagine trying to crack a combination lock. Most locks click the same
  whether you're right or wrong. But imagine a faulty lock that takes
  slightly longer to respond when you get the first digit right. You could
  test all 10 digits, find the one that takes longest (correct!), then
  move to the next digit. Instead of 10,000 guesses (4-digit lock), you
  only need 40 guesses (10 per digit x 4 digits).

  Python's == operator compares strings character by character and stops
  at the first mismatch. If the attacker sends a key starting with "s"
  (correct first character), the comparison takes slightly longer than
  "x" (wrong first character) because it checked one more character
  before failing.

  Additionally, ALL users of the system share the same single API key.
  This means:
  - The server cannot tell who is making a request
  - If one person's key is leaked, EVERYONE is compromised
  - There's no way to revoke access for a single user

■ Real-World Impact on This Project

  - An attacker could theoretically guess the API key by measuring
    response times across thousands of requests
  - Since all doctors/researchers share one key, there's no way to
    know which user performed which action
  - If one researcher's laptop is compromised, the attacker has the
    same access as every other user in the system

■ Detailed Fix Guide

  WHY THIS FIX WORKS:
  Python's == operator compares strings byte by byte and returns False as
  soon as it finds a mismatch. If the first character is wrong, it returns
  almost instantly. If the first 10 characters are correct and the 11th is
  wrong, it takes slightly longer. An attacker can measure these tiny time
  differences to deduce the correct key one character at a time — this is
  called a "timing side-channel attack." hmac.compare_digest() solves this
  by ALWAYS comparing ALL bytes regardless of where the mismatch is. The
  comparison takes the same amount of time whether 0 characters match or
  all characters match — the attacker gets no timing signal. Additionally,
  migrating from a shared API key to per-user JWT tokens solves the
  identity problem: the server can now distinguish WHO is making each
  request, enabling audit logging, per-patient access control, and
  individual key revocation.

  STEP-BY-STEP:
  Immediate fix (timing attack — 15 min):
  1. Open routes_transcript.py
  2. Add "import hmac" at the top
  3. In the _verify_api_key function, replace:
     if api_key != _API_KEY  →  if not hmac.compare_digest(api_key, _API_KEY)
  4. Repeat for routes_nlp.py (same pattern)
  5. Rebuild the backend container
  6. Test: verify that valid and invalid keys still return 200/403 respectively

  Medium-term fix (JWT per-user — 2-4 hours):
  1. Install PyJWT: add "PyJWT>=2.8" to requirements.txt
  2. Create a users table in PostgreSQL (see Vuln 3 detailed guide)
  3. Create a /auth/login endpoint that validates credentials and returns a JWT
  4. Create a verify_jwt dependency that replaces _verify_api_key
  5. Update all router dependencies to use the new JWT verification
  6. Add JWT_SECRET to .env

    # routes_transcript.py — IMMEDIATE fix (constant-time comparison)
    import os
    import hmac
    from fastapi import Header, HTTPException

    _API_KEY = os.environ["API_KEY"]   # Also fixes Vuln 8 (no default fallback)

    async def _verify_api_key(
        x_api_key: str = Header(..., alias="X-API-Key"),
    ) -> str:
        if not hmac.compare_digest(x_api_key, _API_KEY):  # Constant-time!
            raise HTTPException(
                status_code=403,
                detail="Invalid API Key",
            )
        return x_api_key

    # --- MEDIUM-TERM: JWT per-user authentication ---
    # auth.py — new shared authentication module
    import os
    import jwt
    from datetime import datetime, timedelta
    from fastapi import Depends, HTTPException
    from fastapi.security import HTTPBearer
    from passlib.context import CryptContext

    _JWT_SECRET = os.environ["JWT_SECRET"]
    _JWT_ALGORITHM = "HS256"
    _JWT_EXPIRE_HOURS = 8
    _pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")
    _security = HTTPBearer()

    def create_access_token(user_id: int, username: str, role: str) -> str:
        payload = {
            "sub": str(user_id),
            "username": username,
            "role": role,
            "exp": datetime.utcnow() + timedelta(hours=_JWT_EXPIRE_HOURS),
        }
        return jwt.encode(payload, _JWT_SECRET, algorithm=_JWT_ALGORITHM)

    async def verify_jwt(
        credentials = Depends(_security),
    ) -> dict:
        try:
            payload = jwt.decode(
                credentials.credentials, _JWT_SECRET, algorithms=[_JWT_ALGORITHM]
            )
            return payload  # Contains user_id, username, role
        except jwt.ExpiredSignatureError:
            raise HTTPException(401, "Token expired")
        except jwt.PyJWTError:
            raise HTTPException(401, "Invalid token")

    # Login endpoint (add to a new routes_auth.py)
    @router.post("/auth/login")
    async def login(username: str, password: str, db: Session = Depends(get_db)):
        user = db.query(User).filter(User.username == username).first()
        if not user or not _pwd_context.verify(password, user.password_hash):
            raise HTTPException(401, "Invalid credentials")
        token = create_access_token(user.id, user.username, user.role)
        return {"access_token": token, "token_type": "bearer"}

Vulnerability 3: Authorization — No Patient Data Access Control
Severity: CRITICAL | OWASP: A01 Broken Access Control
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ What This Means (Plain Language)

  Imagine a hospital where any doctor with a staff badge can access ANY
  patient's medical records — not just their own patients. Dr. Smith treats
  Patient A, but she can also read Patient B's cancer diagnosis, Patient C's
  lab results, and Patient D's psychiatric notes. The badge gets her through
  the door, but nobody checks which files she's allowed to see.

  In our system, the API key is like the staff badge. Once you have it,
  you can request ANY patient's data — there is no check for "is this
  user authorized to see this specific patient?"

  This also means an attacker can "fish" for patient IDs by trying
  different IDs and checking if they get data back (200 OK) or not
  (404 Not Found). This is called "enumeration" — like an attacker
  calling every room number in a hotel to find out which rooms are
  occupied.

■ Real-World Impact on This Project

  - Any person with the API key can download ALL patients' consultation
    transcripts, NLP scores, and analysis results
  - The batch download endpoint allows getting ALL patient data in a
    single ZIP file with one request
  - Doctor-patient consultation dialogues about cancer prognosis,
    treatment options, and life expectancy are fully exposed
  - Response headers (X-Found-Patients, X-Missing-Patients) explicitly
    tell the attacker which patient IDs exist in the system
  - This constitutes a potential HIPAA violation if real patient data
    is ever used

■ Affected Endpoints (all 4 patient-facing endpoints)

  - GET  /api/transcript/download/{patient_id}        (line 162)
  - GET  /api/transcript/download-batch?patient_ids=   (line 319)
  - GET  /api/transcript/history/{patient_id}          (line 498)
  - GET  /api/transcript/predictions/{patient_id}      (line 562)

  None verify "is this user authorized to access this patient's data?"

■ Attack Scenario D — Unauthorized Cross-Patient Access

  Dr. A only treats sid-01. Dr. B only treats sid-02. Both use same API key.

  Dr. A (legitimate):
    curl -H "X-API-Key: sk_live_abc123..." /api/transcript/download/sid-01
    → 200 OK, sid-01 data — 13,842 bytes (correct)

  Dr. A (unauthorized):

■ Detailed Fix Guide

  WHY THIS FIX WORKS:
  The current system has authentication (verifying WHO you are via API key)
  but no authorization (verifying WHAT you are allowed to access). A single
  shared API key means any authenticated user can access any patient's data.
  The staged fix addresses this incrementally: Stage 1 adds input validation
  to prevent path traversal (quick win). Stage 2 introduces per-user
  identity via JWT tokens and a mapping table that defines which users can
  access which patients. Stage 3 adds role-based access control (RBAC) so
  that different user types (admin, physician, researcher) have different
  permission levels. Each stage builds on the previous one, and each stage
  delivers incremental security improvement without requiring the full
  implementation to be complete.

■ What This Means (Plain Language)

  Imagine a hospital records room with no visitor log, no security cameras,
  and no sign-in sheet. If patient files go missing or are tampered with,
  there is absolutely no way to know who entered the room, what they looked
  at, or when they were there.

  HIPAA (the US health data privacy law) requires that every access to
  patient health information be logged: who accessed it, what they accessed,
  when, and from where. Without this, a data breach cannot even be detected,
  let alone investigated.

■ Real-World Impact on This Project

  - If someone downloads all patient consultation transcripts, there is
    NO record of this happening
  - If a researcher accesses patients outside their study, nobody would know
  - In a HIPAA audit, the absence of access logs would be a serious finding
  - Incident response is impossible — you can't investigate what you didn't log

  No record of who accessed which patient data and when.
  HIPAA requires audit trails for all PHI access.

  Fix: audit_log table recording user_id, action, patient_id, endpoint,
  status, timestamp, ip_address for every patient-data endpoint.

■ Detailed Fix Guide

  WHY THIS FIX WORKS:
  HIPAA requires a record of every access to Protected Health Information
  (PHI): who accessed it, what they accessed, when, and from where. Without
  audit logs, you cannot detect unauthorized access, investigate breaches,
  or demonstrate compliance during an audit. An audit_log table in the
  database creates a tamper-resistant record that persists even if server
  logs are rotated or containers are restarted. A FastAPI middleware
  automatically captures every request to PHI-related endpoints without
  requiring changes to each individual endpoint function. This separation
  of concerns means audit logging is always active and cannot be
  accidentally omitted when new endpoints are added.

  STEP-BY-STEP:
  1. Create the audit_log table in PostgreSQL (via Alembic migration or
     direct SQL)
  2. Create the SQLAlchemy model in models.py
  3. Create a FastAPI middleware that logs all requests to /api/transcript/
     and /api/surveys/ endpoints
  4. The middleware should run AFTER authentication (so it can record the
     user identity) and AFTER the response (so it can record the status)
  5. Add the middleware to the FastAPI app
  6. Test: make several API calls, then query the audit_log table to
     verify records were created
  7. Set up a scheduled job to archive old audit logs (keep at least 6
     years per HIPAA retention requirements)

        __tablename__ = "audit_log"

        id = Column(Integer, primary_key=True, index=True)
        timestamp = Column(DateTime(timezone=True), server_default=func.now())
        user_id = Column(String(255))
        action = Column(String(50), nullable=False)
        endpoint = Column(String(500), nullable=False)
        patient_id = Column(String(255))

    # Step 3: FastAPI middleware (add to main app file)
    import time
    import re
    from starlette.middleware.base import BaseHTTPMiddleware

    _PATIENT_ID_PATTERN = re.compile(
        r"/api/transcript/(?:download|predictions|history)/([^/]+)"
    )
    _AUDITED_PREFIXES = ("/api/transcript/", "/api/surveys/")

    class AuditLogMiddleware(BaseHTTPMiddleware):
        async def dispatch(self, request, call_next):
            # Only audit PHI-related endpoints
            if not any(request.url.path.startswith(p) for p in _AUDITED_PREFIXES):
                return await call_next(request)

            start = time.time()
            response = await call_next(request)
            elapsed_ms = (time.time() - start) * 1000

            # Extract patient_id from URL if present
            match = _PATIENT_ID_PATTERN.search(request.url.path)
            patient_id = match.group(1) if match else None

            # Log to database (non-blocking, best-effort)
            try:
                db = next(get_db())
                log_entry = AuditLog(
                    user_id=request.headers.get("X-API-Key", "unknown")[:8] + "...",
                    action=request.method,
                    endpoint=request.url.path,
                    patient_id=patient_id,
                    ip_address=request.client.host if request.client else None,
                    user_agent=request.headers.get("User-Agent", "")[:500],
                    status_code=response.status_code,
                    response_time_ms=round(elapsed_ms, 2),
                )
                db.add(log_entry)
                db.commit()
            except Exception:
                pass  # Audit failure must not break the request

            return response

    # Step 4: Register the middleware
    app.add_middleware(AuditLogMiddleware)

■ Detailed Fix Guide

  WHY THIS FIX WORKS:
  Security headers instruct the browser to enable built-in protections that
  are disabled by default. Each header addresses a specific attack vector:
  - X-Content-Type-Options prevents the browser from guessing file types
    (MIME sniffing), which attackers exploit to make the browser treat a
    text file as executable JavaScript
  - X-Frame-Options prevents clickjacking, where an attacker embeds your
    site in a hidden iframe and tricks users into clicking buttons
  - Content-Security-Policy (CSP) blocks inline scripts and unauthorized
    external resources, which is the strongest defense against XSS
  - Referrer-Policy prevents your URLs (which may contain patient IDs or
    session tokens) from leaking to third-party sites
  - server_tokens off hides the Nginx version number, denying attackers
    easy identification of known vulnerabilities for that version
  - Permissions-Policy restricts browser features (camera, mic, geolocation)
    that your app does not need, reducing attack surface
  - Strict-Transport-Security (HSTS) forces browsers to always use HTTPS
    (relevant after Vuln 16 is fixed)

  3. Add server_tokens off outside the server block (in the http context)

  4. Rebuild/restart the nginx container:

  5. Test: curl -I http://localhost:3000/ and verify all headers are present
  6. Test with a security header checker (e.g., securityheaders.com) when
     deployed publicly

■ Detailed Fix Guide

  WHY THIS FIX WORKS:
  Rate limiting restricts how many requests a single client (identified by
  IP address) can make within a time window. Without it, an attacker can
  send thousands of requests per second to brute-force API keys, enumerate
  patient IDs, or overwhelm the server (denial of service). Rate limiting

  limits on authentication endpoints vs. data retrieval endpoints). Using
  both layers provides defense-in-depth: Nginx handles bulk floods, and
  slowapi handles per-endpoint abuse.

■ What This Means (Plain Language)

  Imagine sending patient medical records via postcard instead of sealed
  envelope. Anyone who handles the postcard during delivery — the mail
  carrier, the sorting facility, anyone in the office — can read
  everything written on it.

  HTTP (without the S) transmits all data in plain text. This includes:
  - The API key in every request header
  - Patient consultation transcripts
  - NLP analysis scores
  - Survey answers (DCS, SDM, satisfaction responses)
  - REDCap API tokens

  Anyone on the same network (WiFi, corporate LAN) can use freely
  available tools (like Wireshark) to capture and read all this data
  as it flows between the browser and the server.

  Note: This is expected for local development (localhost). It becomes
  a serious problem when deployed on a real network.

■ Current State

  Nginx listens on port 80 (HTTP only).
  No SSL/TLS certificate configuration.
  All traffic is unencrypted.

■ Problem

  - API keys transmitted in plaintext (X-API-Key header)
  - Patient data (PHI) transmitted in plaintext
  - Survey responses transmitted in plaintext
  - REDCap API tokens transmitted in plaintext (backend → REDCap)

■ Fix (Production)

  [Option A] Add SSL/TLS to Nginx:
    listen 443 ssl;
    ssl_certificate /etc/ssl/certs/cert.pem;
    ssl_certificate_key /etc/ssl/private/key.pem;

  [Option B] Use a reverse proxy (Traefik, Caddy) with automatic HTTPS.
  [Option C] Deploy behind a load balancer with SSL termination.

■ Detailed Fix Guide

  WHY THIS FIX WORKS:
  Without TLS/SSL, all data between the browser and server travels as
  plain text over the network. Anyone on the same network segment (WiFi,
  corporate LAN, VPN) can passively capture this traffic using tools like
  Wireshark or tcpdump. TLS encrypts the entire HTTP conversation — headers
  (including the API key), request bodies (patient data, survey answers),
  and response bodies (consultation transcripts, NLP scores). Even if an
  attacker intercepts the traffic, they see only encrypted gibberish. HTTPS
  also verifies server identity, preventing man-in-the-middle attacks where
  an attacker impersonates the server.

  STEP-BY-STEP:
  1. Obtain an SSL certificate:
     - For production: use Let's Encrypt with Certbot (free, automated)
     - For development/internal: use a self-signed cert or mkcert tool
  2. Create a directory for SSL certs in your project:
     mkdir -p nginx/ssl
  3. Install Certbot and obtain certificate (production):
     sudo certbot certonly --standalone -d yourdomain.example.com
  4. Update nginx default.conf to listen on 443 with SSL
  5. Add HTTP-to-HTTPS redirect on port 80
  6. Mount the certificate files into the Nginx container via docker-compose
  7. Set up auto-renewal: certbot renew runs via cron every 12 hours
  8. Test with: curl -I https://yourdomain.example.com (should see 200)

Vulnerability 17: Dockerfile FORWARDED_ALLOW_IPS=*
Severity: LOW | OWASP: A05 Security Misconfiguration
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ What This Means (Plain Language)

  Imagine a building's visitor log where visitors write their own name.
  There's no ID check. An attacker can sign in as "CEO John Smith" and
  the security system records that the CEO was there — when it was
  actually a stranger.

  In web architecture, a reverse proxy (Nginx) sits between users and
  the backend server. Nginx tells the backend the user's real IP address
  via an "X-Forwarded-For" header. FORWARDED_ALLOW_IPS=* means the
  backend trusts this header from ANYONE, not just Nginx. An attacker
  can send a fake X-Forwarded-For header to:
  - Appear to be coming from a different IP address
  - Bypass IP-based restrictions
  - Make audit logs record the wrong source address

■ Vulnerable Code

  Dockerfile:14
    FORWARDED_ALLOW_IPS=*

■ Problem

  Gunicorn/Uvicorn trusts X-Forwarded-For headers from ANY source.
  An attacker can spoof their IP address by sending:
    X-Forwarded-For: 10.0.0.1

  This affects:
  - IP-based rate limiting (if implemented)
  - Access logging (wrong source IP recorded)
  - IP-based access controls

■ Fix

  Set to the specific proxy IP (Nginx container IP):
    FORWARDED_ALLOW_IPS=nginx-container-ip
  Or use Docker network IP range:
    FORWARDED_ALLOW_IPS=172.18.0.0/16

■ Detailed Fix Guide

  WHY THIS FIX WORKS:
  The FORWARDED_ALLOW_IPS=* setting tells Uvicorn/Gunicorn to trust the
  X-Forwarded-For header from ANY IP address. This header is supposed to
  be set only by your reverse proxy (Nginx) to tell the backend the real
  client IP. When you restrict FORWARDED_ALLOW_IPS to only the Nginx
  container's IP (or Docker network subnet), the backend ignores
  X-Forwarded-For headers from all other sources. An attacker sending a
  fake X-Forwarded-For header directly to the backend will have it
  discarded, so the backend sees the attacker's actual IP address. This
  prevents IP spoofing for audit logs, rate limiting, and access controls.

  STEP-BY-STEP:
  1. Find the Nginx container's IP on the Docker network:
     docker inspect prostatecancer-nginx | grep IPAddress
     (typically something like 172.20.0.X)
  2. Open the Dockerfile for the backend service
  3. Change FORWARDED_ALLOW_IPS=* to the specific IP or subnet
  4. Rebuild the backend container:
     docker compose build backend && docker compose up -d backend
  5. Verify by sending a request with a fake X-Forwarded-For header
     and checking that the backend logs the real IP, not the spoofed one

  CODE — BEFORE (vulnerable):
    # Dockerfile (line 14)
    ENV FORWARDED_ALLOW_IPS=*

  CODE — AFTER (fixed):
    # Dockerfile (line 14) — Option A: specific Nginx container IP
    ENV FORWARDED_ALLOW_IPS=172.20.0.2

    # Dockerfile (line 14) — Option B: Docker network subnet
    ENV FORWARDED_ALLOW_IPS=172.20.0.0/16

    # Better: set via docker-compose.yml environment so it can be
    # changed without rebuilding the image:
    # docker-compose.yml → backend → environment:
    #   FORWARDED_ALLOW_IPS: "172.20.0.2"

  PRIORITY & EFFORT: LOW — Fix when convenient | Effort: 5 min
  DEPENDENCIES: None. This is an independent configuration change.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ What This Means (Plain Language)

  Imagine someone slips a booby-trapped note into a patient's file. The

■ Detailed Fix Guide

  WHY THIS FIX WORKS:
  Stored XSS succeeds because user-submitted text is saved to the database
  exactly as received, including HTML tags and JavaScript. When that text is
  later rendered in a browser, the browser executes the embedded scripts as
  if they were part of the application. Sanitizing input with bleach.clean()
  strips or escapes all HTML/JS tags BEFORE storage, so even if the data is
  later rendered unsafely, there is no executable payload. Adding a Content
  Security Policy (CSP) header provides a second layer: even if a payload
  somehow bypasses sanitization, the browser refuses to execute inline
  scripts because the CSP forbids them. Together, these two layers make
  stored XSS exploitation extremely difficult.

  STEP-BY-STEP:
  1. Install the bleach library: add "bleach>=6.0" to requirements.txt
  2. In routes_surveys.py, import bleach at the top of the file
  3. Create a sanitization helper function that strips all HTML tags
  4. Call the sanitizer on every string field in the /submit endpoint
     BEFORE saving to the database (speaker, patient_id, file, survey_type,
     and every value in the answers dict)
  5. Audit the React webapp for any use of dangerouslySetInnerHTML —
     search all .tsx/.jsx files for that string and remove or replace with
     safe rendering
  6. Add CSP header in nginx (ties into Vuln 9 fix):
     add_header Content-Security-Policy "default-src 'self'; script-src 'self'" always;
  7. Test by submitting a survey with <script>alert(1)</script> in the
     speaker field, then verify the stored value has tags stripped

  CODE — BEFORE (vulnerable):

        """Sanitize all string values in the answers dictionary."""
        return {

            for k, v in answers.items()
        }

    @router.post("/submit")
    async def submit_survey(submission: SurveySubmission):
        db_record = SurveySubmissionLog(

    # Stored: "alert(1)"  — script tags stripped, payload neutralized

────────────────────────────────────────────────────────────────────────────────
Fix 1: Timing Attack Mitigation (#2 — Resolved)
────────────────────────────────────────────────────────────────────────────────

Problem:
  API key comparison used Python's `!=` operator, which is vulnerable to timing
  attacks. An attacker can measure response times to deduce the key character by
  character.

  Measured difference: valid key ~45ms vs invalid key ~3ms (clearly distinguishable)

Changes:
  - routes_transcript.py: Added `import hmac`, changed `api_key != _API_KEY`
    to `not hmac.compare_digest(api_key, _API_KEY)`
  - routes_nlp.py: Same change applied

Verification:
  - After fix, both valid and invalid keys return in similar time (~45ms)
  - Attack C timing difference eliminated

────────────────────────────────────────────────────────────────────────────────
Fix 2: Default API Key Fallback Removed (#8 — Resolved)
────────────────────────────────────────────────────────────────────────────────

Problem:
  Both route files used `os.getenv("API_KEY", "default-dev-key")`, meaning the
  server would start and accept "default-dev-key" if the environment variable
  was not set. An attacker could try this well-known default.

Changes:
  - routes_transcript.py: Changed to `os.environ["API_KEY"]` (crashes on startup
    if not set)
  - routes_nlp.py: Same change applied
  - Updated docstrings to reflect "server refuses to start if not set"

Verification:
  - Tested with `X-API-Key: default-dev-key` → 403 Forbidden
  - Tested with no API key → 403 Forbidden
  - Tested with correct key → 200 OK

────────────────────────────────────────────────────────────────────────────────
Fix 3: PostgreSQL Port Removed from Docker (#19 — New, Resolved)
────────────────────────────────────────────────────────────────────────────────

Problem:
  docker-compose.yml exposed PostgreSQL on port 5433 mapped to host `0.0.0.0`,
  allowing direct database access from any machine on the LAN. An attacker on
  the same network could connect and read/modify all patient data.

  Demonstrated: `psql -h localhost -p 5433 -U <user> -d <db>` → full access
  to all tables including patient data, survey submissions, transcript analysis.

Changes:
  - docker-compose.yml: Commented out `ports: ["5433:5432"]` for postgres service
  - Database is now only accessible via Docker internal network

Verification:
  - `psql -h localhost -p 5433` → connection refused
  - All API endpoints still work (backend connects via internal Docker network)

────────────────────────────────────────────────────────────────────────────────
Fix 4: Docker Ports Bound to Localhost (#20 — New, Resolved)
────────────────────────────────────────────────────────────────────────────────

Problem:
  Backend (port 8000) and Nginx (port 3000) were bound to `0.0.0.0`, making the
  entire application accessible to any device on the local network. Combined with
  the survey endpoints having no authentication, any LAN device could access and
  modify patient data.

Changes:
  - docker-compose.yml: Changed backend port from `"8000:8000"` to
    `"127.0.0.1:8000:8000"`
  - docker-compose.yml: Changed nginx port from `"3000:80"` to
    `"127.0.0.1:3000:80"`

Verification:
  - Services only respond on localhost (127.0.0.1)
  - External/LAN access blocked

Fix 5: Path Traversal Prevention (#1 — Resolved)
────────────────────────────────────────────────────────────────────────────────

Problem:
  patient_id parameter had no input validation. An attacker could send
  "../../etc/passwd" as the patient ID to read or write files outside the
  uploads directory. File write was confirmed inside the Docker container.

Changes:

    (alphanumeric, hyphens, underscores only)
  - Added `_validate_patient_id()` function with defense-in-depth:
    Layer 1: Regex whitelist rejects dots, slashes, special characters
    Layer 2: resolve() check verifies path stays inside uploads directory
  - Applied to: `_xlsx_path()`, `_save_xlsx()`, `_get_xlsx_bytes()`,
    `history` endpoint, `predictions` endpoint
  - `download` and `download-batch` are covered via `_xlsx_path()` calls

Verification:

  - Path traversal (../../etc/passwd): 400 "Invalid patient_id format"
  - download-batch traversal: 400 "Invalid patient_id format"
